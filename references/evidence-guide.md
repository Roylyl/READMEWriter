# Claim → Evidence

对影响使用决策的声明核对来源：安装条件、平台能力、版本、性能、隐私及发布入口。证据用于内部事实判断，不要求把来源等级、检查过程或设备验证记录写进README。日常写作无需生成证据文件；仅用户要求证据记录、审计或评估任务需要时保存独立evidence JSON，交付位置遵循项目已有文档约定。

## 证据如何约束措辞

下表用于内部判断事实范围；其中构建、模拟器与设备记录的表述只适用于用户明确要求的验证说明，或项目本身需要呈现实验结果的场景，不作为普通README的写作模板。

| 证据等级 | 能支持的表述 | 不能直接推出 |
| --- | --- | --- |
| configuration | 项目配置目标为 iOS 26；清单声明 Python 3.10+ | 每个版本或设备已通过验证 |
| implementation | 源码包含某入口或实现 | 功能在目标环境运行成功 |
| build | 指定环境构建通过 | 实际使用、签名发行或端到端成功 |
| simulation | 在指定模拟器或合成输入下通过某项检查 | 真机性能、温升、续航或准确率 |
| device | 在注明设备、版本、输入和条件下实测通过 | 所有设备或长期稳定性 |
| release | 对应标签、附件、校验值和发布记录已核实 | 同名源码分支和所有安装包完全一致 |
| unknown | 暂无可核实记录；当前未确认 | 乐观补全为支持或通过 |

这些是不同范围的证据，不是单向升级的分数。实机音频测试不能证明网络隐私；Release 存在不能证明正确性。配置、实现和测试结论冲突时，缩小声明或呈现差异。

例如只有`IPHONEOS_DEPLOYMENT_TARGET = 26.0`时，在运行要求中写“最低系统版本：iOS26.0”。SDK版本不代表最低系统版本，不要把最低配置扩大为完整兼容承诺。即使存在iPhone实机记录，普通项目README也不主动描述设备验证经历；仅明确请求的验证报告才注明设备、系统和操作范围。

## 记录格式

以下为格式示例，不代表任何真实项目的验证结果：

```json
{
  "schema_version": 1,
  "claims": [
    {
      "id": "ios-deployment-target",
      "quote": "最低系统版本：iOS26.0。",
      "level": "configuration",
      "reasoning": "工程配置声明部署目标；没有设备记录，因此不宣称真机验证。",
      "evidence": [
        {
          "path": "Demo.xcodeproj/project.pbxproj",
          "excerpt": "IPHONEOS_DEPLOYMENT_TARGET = 26.0;"
        }
      ]
    }
  ]
}
```

`quote`必须逐字出现在最终README。证据路径相对于`--root`，摘录必须存在。默认不计算或增加文件哈希；仅任务涉及文件完整性、下载校验、安全验证或用户明确要求时使用可选`sha256`字段。`unknown`可无证据，仅用于确实需要向读者说明的关键缺项，不为缺少测试记录批量生成未知声明。其余等级至少一条证据。

外部事实应记录完整公开 URL、查询日期和关键摘录到项目允许的本地证据记录，再引用该记录；不保存访问令牌或私人日志。文件存在并不意味着记录可信，需人工核查来源和时间。

## 双层检查

1. `validate_readme.py --evidence evidence.json` 检查 JSON 结构、声明存在、证据文件与摘录、可选哈希和路径范围。
2. Agent / 评审者确认：证据是否真的支持这句话？适用对象、版本、设备、环境与日期是否一致？有没有更强的结论或未覆盖的关键声明？

脚本不自动判定自然语言含义，不会发现所有遗漏声明，也不能防止作者编造一份看似一致的记录。禁止把完整性检查描述为“事实自动验证通过”。
