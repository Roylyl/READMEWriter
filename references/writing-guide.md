# 结构与写作规范

## 首屏与阅读顺序

首屏依次提供项目图标（存在时）、唯一一级标题、一句话定位、状态徽章和关键入口。读者应能快速判断“是什么、适合谁、如何开始”。标题下的一句话交代对象与用途，避免抽象口号和未经证明的比较级。

品牌区可居中，正文保持默认左对齐。导航优先提供安装、功能、预览、开发、许可等真实存在的入口；较长 README 再增加目录，不重复堆放两套相同导航。重要状态只有影响开始使用时才前置。

## 按项目选择章节

使用 [15 类项目规范](project-profiles.md) 及其 [结构化数据](project-profiles.json) 确定必须回答的信息、建议内容、禁止的默认推断与检查目标。混合项目选择主类型加必要的次类型，合并重复项；不要创建与实际功能无关的空章节。

先解决“如何使用”和“证据支持到哪里”，再决定顺序与篇幅。详细安装、协议或验证记录已有独立文档时，保留入口和关键结论即可。

## 正式措辞

- 先描述行为，再给条件与结果。例如：“在页面中显示双语对照；首次启用前需要配置自己的 API 服务。”
- 功能列表使用“**能力名称：**具体行为与收益”，并列粒度一致。避免“强大、极致、完美、零风险、全平台、生产就绪”等没有证据支撑的宣传语。
- 正文标题采用语义明确的中文，不默认添加 emoji、连续感叹号或装饰性分隔线。专业术语、产品名和命令保留原文。
- 固定版本来自对应配置并链接源文件；不要为提升视觉效果杜撰版本号。历史验证带上必要环境，避免随时间失效的“最新”“目前全部通过”。
- 参数、平台、规格、命令差异适合表格；操作流程用有序列表；背景与限制用短段落。不把长说明塞进超宽表格。
- 详细协议、完整构建矩阵和长排错清单留在独立文档，通过相对链接进入。没有请求时不要为了缩短 README 大规模迁移现有资料。

## 可操作的上手说明

写清前提、获取方式、执行位置、启动动作和可见结果。安装包路径、文件名和参数按实际文件核实。多平台命令确有差异时分开写；不要默认所有读者都使用作者的操作系统。

示例使用公开值或明确占位符，不包含作者本机绝对路径、账户凭据、私有域名与日志隐私。可复制命令不要混入终端提示符。只有教程模板保留占位符；交付项目 README 中应消除能从仓库确认的占位符。

自动安装提示词可作为技能或资源包的可选便利入口，限定安装对象与目标目录；不能替代手动步骤，也不能把“读取 README”解释为安装授权。

## 交付前检查

- 一级标题唯一、层级连续，导航能对应标题；含标点、数字、重复标题时特别检查锚点。
- 相对链接从所在文档解析，目标文件存在且大小写一致；图片有说明，图标没有误标为实际产品截图。
- 徽章表达真实状态，颜色和样式一致，点击目的地匹配标签；没有虚构通过、许可、兼容或下载统计。
- 命令与仓库脚本一致，使用说明与开发说明分开，构建产物和源码不混淆。
- 没有模板残留、未经确认的法律声明、私密路径或照抄的参考项目专属信息。
- 如仅静态核对文档，明确说明未运行产品；不为文档改动添加重复实现的测试。

## 实验与评测文档

涉及性能、模型或跨设备比较时，注明单位、测量起止点和环境；相似名称的指标不一定可比。能力矩阵描述各平台真正可用的功能，不能将主平台能力扩展成所有客户端的承诺。验证记录可用“检查内容—证据文件—范围”表格，历史日志链接到独立文档，正文只保留影响使用的结论。
